# External services and independent runtime review — 5 September 2026

## Independent review of runtime changes

Read the current authentication SDK, session revocation store, native/Supabase auth, shared API throttles, production origin/CSP middleware, LLM budget accounting and transport, SSRF guard, MySQL pool/TLS policy, server lifecycle/readiness and privacy-filtered observability. Findings were sent to the coordinating reviewer before changes outside the assigned ownership were made.

- Production API/AI budgets fail closed when persistent accounting is unavailable; account/global counters remain bounded. Sessions include issuer, audience, expiry and a revocable identifier, and session verification fails closed on storage failure. The LLM transport has bounded contexts, token caps, response body size and execution/concurrency limits; it does not automatically retry paid malformed generations. This review did not identify an additional demonstrated direct authorization bypass in those changes.
- Readiness initially did not check the new human-decision migration. The coordinating worker added a check for `applications.humanDecisionAt`.
- An owner alert initially resolved `OWNER_EMAIL` without checking the account's role. A native account claiming that unverified address could receive an application alert. The owned accelerated pipeline now sends the in-app owner alert only to an admin role.
- Staff MFA is now checked on all private exports that allow staff to read another applicant's record and on inspector bundles, in addition to the main staff API guard. A signed `aal2` claim from the configured institutional identity provider is required in production by default.
- Deployment-dependent limitations remain: the configured trusted proxy hop count must match actual ingress; direct-origin access can undermine per-IP identity even though independent global auth/strict ceilings remain. DNS checks do not pin the connection address, so network egress restrictions and a narrow trusted-host allowlist remain necessary against DNS rebinding. Supabase owner-email bootstrap relies on a signed top-level email-confirmation claim that is not present in all access-token configurations; prefer an explicitly configured owner subject instead of weakening verification.

## Additional implementations

- Literature requests have a shared bounded HTTP queue, HTTPS/SSRF checks, blocked redirects, bounded response bodies, and at most one read-only GET retry. Metered Elicit POSTs are not retried automatically. API keys are URL-encoded when required by the source. Provider response bodies/network exceptions are not returned to users or AI as diagnostic text.
- Concurrent identical literature requests share one operation. Cache keys now include relevance threshold and result cap; callers receive independent copies. Before this change, changing the filter could return a prior cached result and one caller could mutate another caller's cached array.
- Arabic letters are preserved during lexical relevance scoring. An unrelated abstract no longer receives a relevance bonus large enough to pass the default threshold with zero query overlap. Returned source URLs must be HTTPS without credentials; unsafe URLs are removed. These are lexical/structural checks, not scientific validation or verified full text.
- Missing/malformed source totals remain unavailable. ClinicalTrials.gov explicitly requests `countTotal` and uses the returned count; a truncated page length is no longer presented as the full database result count. Invalid response containers are source failures, not zero-result searches. Unconfigured Elicit remains visible as not configured. PubMed results are labelled indexed literature, rather than automatically asserting peer review.
- In-app notifications retain sensitive details behind authentication. External owner pushes contain only a generic sign-in notice, never applicant titles, identifiers, support text or adverse-event reasons. An optional unconfigured notification integration returns false instead of failing an already committed application mutation. Delivery is bounded, HTTPS-only, guarded against SSRF and redirects, and never logs provider response bodies.
- Notification records normalize legacy unsupported event types to `general`, cap title/message fields, and sanitize controls. Unread counts use a database aggregate rather than loading every notification. Unavailable notification storage is not reported as zero. Approval notices no longer claim a document has already generated, and issuance notices no longer invent one-year validity.
- Maps proxy access now accepts only known endpoint paths, rejects traversal/callback/caller key overrides, requires bounded scalar parameters and request bodies, uses a bounded queue and request deadline, checks HTTPS/SSRF, blocks redirects and limits response bodies. Provider errors never echo the credential-bearing URL or raw body. The proxy's required API key stays server-side.
- Stage 2 AI review requests no longer duplicate twelve protocol suggestions both inside field scores and a second model-output object. The server derives the existing UI suggestion map from the validated field rows, reducing the risk of exhausting the bounded interactive completion budget.

## Tests and limits of evidence

The combined owned test suite passed **65 tests across 15 files**, including 19 additional literature/external-channel/notification cases. The export tests also verify authenticated generation, provenance-gated public records, no-store/sandbox/noindex headers, and malformed IDs. All source/network behavior in these tests was mocked or loopback-only; no real notification, email, maps request, model request, or scholarly search containing applicant data was sent.

Real PDF/DOCX verification is recorded separately in `docs/audit-ai-documents.md` and `docs/validation/ai-documents/generator-validation.json`. Live provider entitlements, contractual/residency requirements, source terms, MFA enrollment, production ingress topology, backup restoration, clinical calibration, production capacity and legal authority require their own operational evidence.
