## Public discovery implementation

`shared/seo.ts` exposes the bilingual public route contract and strict canonical-origin validation. `shared/guidelineMetadata.ts` keeps full guideline content out of the initial route-metadata bundle; a regression test prevents metadata drift. The root build consumes this contract to generate public HTML/sitemap. `RouteMetadata` updates title, description, Open Graph, canonical and noindex state on SPA navigation.

The generic fallback HTML is noindex. Public resource/home/policy/about/support/generic verification pages may be indexed. Authentication, application, chat, reviewer/admin, individual certificate references, registry/statistics and unknown URLs are excluded from public indexing. Authentication and server authorization protect information; robots rules are not an access-control boundary.

The current language toggle produces Arabic and English interface content, but does not establish separate indexable language URLs. No fabricated hreflang pairs were added. Dedicated bilingual route URLs and corresponding server content are a future improvement that needs its own routing and indexing verification.

`MARKETING.md` contains Saudi buyer priorities, pilot-to-launch sequence, bilingual campaign drafts, discovery/measurement plan, and a publication claims register. Domain purchase, approved pricing, real data-controller and reviewer/institution records, legal/provider/region/retention details, operational staffing and actual ad account setup remain external launch requirements.

When `VITE_PUBLIC_DEMO_BANNER=1`, a bilingual global evaluation banner appears on every route, including authentication and submissions. It instructs visitors to use synthetic data only and exclude participant, patient and confidential research information. The flag is an operator-facing deployment safeguard, not proof that backend production gates are complete.

## Institutional authentication boundary

Profile remains accessible to signed-in users with an ordinary session. Staff authority requires the server-configured two-factor control. The UI never treats a configured provider, successful enrollment, matching email address, or administrator label as proof of two-factor verification. It requires the same Supabase subject as the platform account, verifies the code, bridges the verified token to the server, and reads the resulting app session before showing confirmation. QR material stays in React memory and an image context, with no live SVG insertion or persisted setup secret. All setup and removal actions are explicit user actions.

Native password accounts need a separately authenticated and appointed institutional account for staff authority; roles and historical applications are not silently migrated by email. Operator bootstrap and account recovery require documented institutional procedures. This repository does not contain evidence that an actual production Supabase tenant, MFA recovery policy, or reviewer identity is configured.
